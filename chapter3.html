🌿3.1 브랜치란 무엇인가?

브랜치(Branch)는 독립적인 작업 경로입니다. 나무의 가지처럼, 메인 가지에서 새로운 가지를 만들어 작업한 후 다시 합칠 수 있습니다.

브랜치가 필요한 이유

  • 병렬 작업: 여러 기능을 동시에 개발
  • 안전성: 메인 코드에 영향을 주지 않음
  • 코드 리뷰: 다른 팀원이 확인 후 병합
  • 실험: 새로운 아이디어를 테스트
master (메인 브랜치) | |-- feature/login (로그인 기능) |-- feature/payment (결제 기능) |-- bugfix/header (헤더 버그 수정)

기본 개념

용어 설명
master/main 기본 브랜치, 항상 안정적인 코드
feature 브랜치 새로운 기능 개발용
bugfix 브랜치 버그 수정용

✨3.2 브랜치 만들고 전환하기

따라하기

Step 1: 새 브랜치 생성
git branch feature/login

이 명령어는 "feature/login"이라는 브랜치를 만듭니다.

Step 2: 브랜치로 이동
git checkout feature/login

이제 이 브랜치에서 작업합니다.

Step 3: 확인하기
git branch

현재 브랜치 앞에 "*" 기호가 붙습니다.

한 번에 생성과 이동

이 두 작업을 한 번에 할 수도 있습니다:

git checkout -b feature/login

또는 최신 Git에서는:

git switch -c feature/login
💡 브랜치 이름 짓는 팁
✅ feature/login, bugfix/header, docs/readme
❌ asdf, new, test, update

현재 브랜치에서 작업하기

Step 1: 파일 수정
echo "Login page" > login.html
Step 2: 커밋
git add .
git commit -m "Add login page"
Step 3: 마스터로 돌아가기
git checkout master

마스터에는 login.html 파일이 없습니다! (아직)

📌 브랜치의 독립성
각 브랜치는 독립적입니다. 한 브랜치에서의 변경이 다른 브랜치에 영향을 주지 않습니다.

🔗3.3 브랜치 병합하기 (Merge)

브랜치에서 작업을 완료했으면, 이를 마스터 브랜치에 합쳐야 합니다. 이것을 "병합(Merge)"이라고 합니다.

따라하기

Step 1: 마스터 브랜치로 이동
git checkout master
Step 2: feature/login 브랜치 병합
git merge feature/login

마스터 브랜치에 feature/login의 변경사항이 포함됩니다!

Step 3: 확인하기
git log --oneline

이제 login.html 파일이 마스터에도 있습니다!

브랜치 삭제하기

병합이 완료된 브랜치는 삭제해도 됩니다:

git branch -d feature/login
🎯 병합 흐름
1. feature 브랜치 생성 (git branch)
2. 기능 개발 (git add, git commit)
3. master로 이동 (git checkout master)
4. feature 병합 (git merge feature/...)
5. feature 삭제 (git branch -d)

⚠️3.4 충돌 해결하기 (Conflict)

두 브랜치에서 같은 파일의 같은 부분을 수정했을 때 "충돌(Conflict)"이 발생합니다. 이를 수동으로 해결해야 합니다.

충돌이 발생하는 상황

  • 같은 파일의 같은 부분을 다르게 수정했을 때
  • 한 브랜치에서 파일을 삭제했을 때

충돌 해결 방법

Step 1: 충돌 발생 시 git merge 다시 시도
git merge other-branch

Git에서 충돌을 알립니다.

Step 2: 충돌한 파일 확인
git status

"both modified" 파일을 찾습니다.

Step 3: 파일 편집

파일을 열면 다음과 같이 보입니다:

<<<<<<< HEAD
현재 브랜치의 코드
=======
다른 브랜치의 코드
>>>>>>> other-branch

이 표시들과 필요없는 코드를 모두 삭제하고, 최종 코드만 남깁니다.

Step 4: 해결 후 커밋
git add .
git commit -m "Resolve merge conflict"
💡 충돌 피하기
- 작은 단위로 자주 커밋하기
- 브랜치 병합 전에 pull 하기
- 팀원과 어느 파일을 수정할지 미리 논의하기

🔀3.5 Pull Request와 협업 워크플로우

실제 팀 프로젝트에서는 보통 "Pull Request(PR)"를 통해 코드 리뷰 후에 병합합니다.

Pull Request란?

PR은 "내 변경사항을 검토해주세요"라는 요청입니다. GitHub, GitLab 같은 사이트에서 사용합니다.

협업 워크플로우 (GitHub 기준)

Step 1: feature 브랜치에서 작업
git checkout -b feature/new-page
# 파일 수정
git add .
git commit -m "Add new page"
Step 2: 원격에 push
git push origin feature/new-page
Step 3: GitHub에서 Pull Request 생성

GitHub 웹사이트에서:

  • 브랜치 선택
  • "Create Pull Request" 클릭
  • 제목과 설명 작성
  • "Create Pull Request" 완료
Step 4: 코드 리뷰 (팀원)

팀원들이 코드를 검토하고 의견을 댓글로 남깁니다.

Step 5: 수정 및 재push (필요시)
git add .
git commit -m "Address review comments"
git push origin feature/new-page

PR이 자동으로 업데이트됩니다!

Step 6: 병합

리뷰가 완료되면 GitHub에서 "Merge Pull Request" 클릭!

확인해보기

git checkout master
git pull origin master
# feature 브랜치 삭제
git branch -d feature/new-page
🎯 PR의 장점
✅ 코드 품질 관리
✅ 지식 공유
✅ 버그 예방
✅ 협업 기록
