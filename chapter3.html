3장: 협업하기 - 브랜치와 병합

팀과 함께 효율적으로 작업하는 방법을 배워봅시다!

🎯 이 장을 마치면 다음을 할 수 있습니다:

  • 브랜치를 만들고 전환하며 독립적으로 작업할 수 있다
  • 브랜치를 병합(merge)하여 작업을 합칠 수 있다
  • 충돌(conflict)이 발생했을 때 직접 해결할 수 있다
  • Pull Request를 만들어 코드 리뷰를 요청할 수 있다
  • 해시값(커밋 ID)이 무엇인지 이해할 수 있다
← 이전 장 다음 장 →

💡왜 배우나요?

혼자 작업할 때는 add, commit, push만으로 충분합니다. 하지만 팀으로 작업하면 이런 상황이 생깁니다:

  • "로그인 기능"과 "결제 기능"을 동시에 개발하고 싶다
  • 실험적인 코드를 시도해보고 싶지만, 원본을 망치고 싶지는 않다
  • 팀원의 코드와 내 코드를 합쳐야 한다

브랜치가 이 모든 문제를 해결합니다!

🔑3.1 커밋 ID(해시값) 이해하기

📌 용어: 해시값 (커밋 ID)

한글 정의: 각 커밋에 자동으로 부여되는 고유한 식별 번호입니다. a1b2c3d처럼 영문자와 숫자의 조합입니다.

일상 비유: 택배 송장 번호와 같습니다. 모든 택배에는 고유한 번호가 있어서, 그 번호만 있으면 정확히 어떤 택배인지 찾을 수 있죠. 커밋 해시값도 마찬가지입니다.

왜 필요한가? "3번째 전 커밋"이라고 하면 사람마다 다르게 셀 수 있지만, a1b2c3d라고 하면 정확히 하나의 커밋을 가리킵니다.

직접 해보기

Step 1: 커밋 해시값 확인하기
$ git log --oneline

📊 예상 결과:

b2c3d4e (HEAD -> master) Add awesome message
a1b2c3d Add learning message to hello.txt
f6e5d4c Add hello.txt file

앞의 7자리(b2c3d4e)가 해시값의 축약형입니다. 전체 해시값은 40자리이지만, 앞 7자리만 사용해도 됩니다.

Step 2: 특정 커밋 내용 보기
$ git show a1b2c3d

해당 커밋에서 무엇이 변경되었는지 상세히 보여줍니다. 나가려면 q를 누르세요.

📌 용어: HEAD

한글 정의: 현재 내가 위치한 커밋을 가리키는 포인터입니다.

일상 비유: 책을 읽을 때 끼워두는 책갈피와 같습니다. "지금 여기를 보고 있다"를 표시합니다.

왜 필요한가? Git은 HEAD를 기준으로 "여기서부터 변경된 내용"을 파악합니다. HEAD~1은 "현재 위치에서 1개 전 커밋"을 의미합니다.

✅ 이해 완료!
해시값은 커밋의 "택배 송장 번호"이고, HEAD는 "지금 내 위치 책갈피"입니다.

🌿3.2 브랜치란 무엇인가?

📌 용어: 브랜치 (Branch)

한글 정의: 메인 코드에서 독립적으로 분리된 작업 경로입니다.

일상 비유: 평행 우주를 상상해보세요. 원래 세계(master)는 그대로 유지되면서, 평행 우주(브랜치)에서 자유롭게 실험합니다. 결과가 좋으면 원래 세계에 합칩니다. 마음에 안 들면 평행 우주를 없애면 됩니다.

왜 필요한가? 브랜치 없이 작업하면, 미완성 코드가 팀 전체에 영향을 줍니다. 브랜치를 사용하면 각자 독립적으로 작업하고, 완성된 것만 합칠 수 있습니다.

master (메인 브랜치) ----o----o----o----o----o--- \ / feature/login (로그인 기능) o----o----o--- \ feature/payment (결제 기능) o----o---
용어 설명 비유
master/main 기본 브랜치, 항상 안정적인 코드 원래 세계
feature 브랜치 새로운 기능 개발용 실험용 평행 우주
bugfix 브랜치 버그 수정용 수리 작업용 평행 우주

✨3.3 브랜치 만들고 전환하기

직접 해보기: 브랜치 생성부터 커밋까지

Step 1: 현재 브랜치 확인
$ git branch

📊 예상 결과:

* master

*가 현재 위치한 브랜치를 표시합니다.

Step 2: 새 브랜치 만들고 이동하기
$ git checkout -b feature/greeting

📊 예상 결과:

Switched to a new branch 'feature/greeting'

-b는 "브랜치를 만들면서(branch) 바로 이동"하는 옵션입니다.

Step 3: 브랜치에서 작업하기
$ echo "Welcome to my project!" > welcome.txt
$ git add welcome.txt
$ git commit -m "Add welcome page"
Step 4: master로 돌아가서 확인하기
$ git checkout master
$ ls

📊 결과: welcome.txt가 없습니다! master에서는 아직 이 파일이 존재하지 않습니다.

$ git checkout feature/greeting
$ ls

📊 결과: welcome.txt가 다시 나타납니다! 브랜치별로 파일이 독립적으로 관리됩니다.

✅ 성공!
브랜치를 만들고 독립적으로 작업하는 것을 확인했습니다!
💡 브랜치 이름 짓기 규칙
✔ 좋은 예: feature/login, bugfix/header, docs/readme
✘ 나쁜 예: test, new, asdf
"종류/설명" 형식으로 짓는 것이 좋습니다.
💡 최신 Git(2.23+)에서는 switch 명령어도 사용 가능합니다
git switch -c feature/greeting (새 브랜치 만들고 이동)
git switch master (브랜치 이동)
checkout보다 직관적인 이름이지만, 둘 다 같은 기능입니다.

🔗3.4 브랜치 병합하기 (Merge)

📌 용어: 병합 (Merge)

한글 정의: 두 개의 브랜치를 하나로 합치는 작업입니다.

일상 비유: 평행 우주에서 실험한 결과가 좋으니, 원래 세계에 그 결과를 적용하는 것입니다.

왜 필요한가? 브랜치에서 만든 기능을 실제 프로젝트에 반영하려면 병합이 필수입니다.

직접 해보기: 병합 실습

Step 1: master 브랜치로 이동
$ git checkout master

병합은 항상 "합쳐질 브랜치"에서 실행합니다. master에 feature를 합치려면, master에 있어야 합니다.

Step 2: feature/greeting 브랜치 병합
$ git merge feature/greeting

📊 예상 결과:

Updating a1b2c3d..d4e5f6a
Fast-forward
welcome.txt | 1 +
1 file changed, 1 insertion(+)
Step 3: 결과 확인
$ ls

이제 master에도 welcome.txt가 있습니다!

$ git log --oneline

feature/greeting의 커밋이 master에 포함되었습니다.

Step 4: 사용한 브랜치 삭제
$ git branch -d feature/greeting

📊 예상 결과:

Deleted branch feature/greeting (was d4e5f6a).

병합이 완료된 브랜치는 삭제해도 안전합니다. 변경사항은 이미 master에 포함되어 있습니다.

✅ 성공!
브랜치를 만들고, 작업하고, 병합하고, 삭제하는 전체 흐름을 완료했습니다!
📌 병합 전체 흐름 정리
1. git checkout -b feature/이름 (브랜치 만들기)
2. 파일 수정 → git add → git commit (작업하기)
3. git checkout master (master로 이동)
4. git merge feature/이름 (병합하기)
5. git branch -d feature/이름 (브랜치 삭제)

⚠️3.5 충돌 해결하기 (Conflict)

📌 용어: 충돌 (Conflict)

한글 정의: 두 브랜치에서 같은 파일의 같은 부분을 다르게 수정했을 때, Git이 어느 쪽을 선택할지 모르는 상황입니다.

일상 비유: 두 사람이 같은 문서의 같은 문단을 동시에 다르게 고쳤을 때, 컴퓨터가 "어느 쪽이 맞나요?"라고 물어보는 것입니다.

왜 필요한가? 충돌은 정상적인 상황입니다. Git이 여러분 대신 임의로 결정하지 않고, 사람에게 판단을 맡기는 것입니다. 이것은 Git이 여러분을 돕고 있는 것입니다!

안심하세요

충돌은 무서운 것이 아닙니다! 충돌이 발생해도 파일이 깨지거나 데이터가 손실되지 않습니다. Git이 양쪽 변경사항을 모두 보여주고, 여러분이 직접 선택하면 됩니다.

직접 해보기: 충돌 만들고 해결하기

충돌을 직접 만들어보면 더 이상 두렵지 않을 것입니다!

Step 1: master에서 파일 수정
$ git checkout master
$ echo "Hello from master branch!" > greeting.txt
$ git add greeting.txt
$ git commit -m "Add greeting from master"
Step 2: 새 브랜치에서 같은 파일을 다르게 수정
$ git checkout -b feature/alt-greeting
$ echo "Hello from feature branch!" > greeting.txt
$ git add greeting.txt
$ git commit -m "Add greeting from feature"
Step 3: 병합 시도 - 충돌 발생!
$ git checkout master
$ git merge feature/alt-greeting

📊 예상 결과:

Auto-merging greeting.txt
CONFLICT (content): Merge conflict in greeting.txt
Automatic merge failed; fix conflicts and then commit the result.

Git이 "greeting.txt에서 충돌이 발생했으니, 직접 해결해주세요"라고 말하고 있습니다.

Step 4: 충돌 파일 확인
$ cat greeting.txt

📊 예상 결과:

<<<<<<< HEAD
Hello from master branch!
=======
Hello from feature branch!
>>>>>>> feature/alt-greeting

이 표시의 의미:

  • <<<<<<< HEAD부터 =======까지: master(현재 브랜치)의 내용
  • =======부터 >>>>>>>까지: feature/alt-greeting의 내용
Step 5: 충돌 해결하기

텍스트 에디터(메모장, VS Code 등)로 greeting.txt를 열고, 원하는 내용만 남깁니다.

예를 들어, 두 내용을 모두 사용하고 싶다면:

Hello from master branch!
Hello from feature branch!

<<<<<<<, =======, >>>>>>> 표시를 모두 삭제하고 최종 내용만 남기면 됩니다.

또는 한쪽만 선택할 수도 있습니다:

Hello from master branch!
Step 6: 해결 완료 - 커밋하기
$ git add greeting.txt
$ git commit -m "Resolve merge conflict in greeting.txt"
Step 7: 브랜치 정리
$ git branch -d feature/alt-greeting
✅ 성공!
충돌을 직접 만들고 해결했습니다! 이제 충돌은 더 이상 무서운 것이 아닙니다.
💡 충돌 줄이는 방법
- 작은 단위로 자주 커밋하기
- 병합 전에 항상 git pull로 최신 코드 받기
- 팀원과 어느 파일을 수정할지 미리 이야기하기
- 한 파일을 여러 명이 동시에 수정하지 않기

🔀3.6 Pull Request로 협업하기

📌 용어: Pull Request (PR)

한글 정의: "내 변경사항을 검토해주세요"라는 요청입니다. GitHub에서 코드 리뷰 후 병합하는 공식적인 절차입니다.

일상 비유: 문서를 직접 최종본에 붙이는 대신, "이렇게 수정했는데 괜찮을까요?"라고 동료에게 검토를 요청하는 것입니다.

왜 필요한가? 코드 리뷰를 통해 버그를 미리 발견하고, 팀원 간 지식을 공유할 수 있습니다.

PR은 함께 배우는 과정입니다

PR에서 수정 요청을 받는 것은 자연스러운 일입니다. 실력이 부족해서가 아니라, 다른 관점에서 더 좋은 코드를 함께 만드는 과정입니다.

직접 해보기: PR 만들기 (GitHub)

Step 1: 새 브랜치에서 작업 후 push
$ git checkout -b feature/about-page
$ echo "About page content" > about.txt
$ git add about.txt
$ git commit -m "Add about page"
$ git push -u origin feature/about-page
Step 2: GitHub에서 PR 생성
  1. GitHub 저장소 페이지로 이동합니다
  2. "Compare & pull request" 버튼이 나타납니다 - 클릭!
  3. 제목: "Add about page" 입력
  4. 설명: 어떤 변경을 했는지 간단히 작성
  5. "Create pull request" 클릭
Step 3: 코드 리뷰 받기

팀원들이 PR 페이지에서 코드를 보고 댓글을 남깁니다.

  • 수정이 필요하면: 로컬에서 수정 → commit → push (PR이 자동 업데이트)
  • 승인받으면: "Merge pull request" 클릭!
Step 4: 병합 후 정리
$ git checkout master
$ git pull origin master
$ git branch -d feature/about-page
✅ 성공!
첫 번째 Pull Request를 만들었습니다!

📚3장 핵심 요약

명령어 역할 사용 장면
git branch 브랜치 목록 보기 현재 브랜치 확인
git checkout -b 이름 새 브랜치 만들고 이동 새 기능 시작
git checkout 이름 다른 브랜치로 이동 브랜치 전환
git merge 이름 브랜치 합치기 기능 완성 후 병합
git branch -d 이름 브랜치 삭제 병합 후 정리
git push -u origin 이름 브랜치를 GitHub에 올리기 PR 생성 전
git log --oneline 커밋 해시값 확인 특정 커밋 참조 시
