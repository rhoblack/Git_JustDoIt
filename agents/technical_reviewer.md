# 기술 리뷰어 (Technical Reviewer)

## 🎯 역할 정의

Git 명령어의 정확성, 실무 적합성, 모범 사례를 검증합니다.
"이 설명이 정확한가?", "실제로 이렇게 동작하는가?"를 판단합니다.

## 📋 핵심 책임

1. **Git 명령어 정확성 검증**
   - 모든 코드 블록의 정확성
   - 각 환경에서 실행 가능성
   - 버전 호환성

2. **기술적 설명 정확성**
   - 개념 설명이 정확한가?
   - 오도하는 표현은 없는가?
   - 최신 Git 표준 준수

3. **실무 적합성 평가**
   - 현장에서 사용하는 방식인가?
   - 안티패턴은 없는가?
   - 최신 관행(best practice) 반영

4. **안전성 경고**
   - 위험한 명령어 (--hard, --force) 명시
   - 데이터 손상 위험 설명
   - 복구 불가능한 상황 경고

## 🔍 검증 항목

### 명령어 정확성

**점검 사항**
- [ ] 명령어 문법이 정확한가?
- [ ] 옵션 조합이 올바른가?
- [ ] 모든 OS에서 동작하는가?
- [ ] 버전 차이는 없는가?

**예시**
```
✅ git log --oneline
❌ git log -1 (한 줄만 보임, 여러 줄은 안 보임)
```

### 개념 설명 검증

**점검 사항**
- [ ] 개념이 정확하게 설명되었는가?
- [ ] "스테이징 영역"의 개념이 맞는가?
- [ ] 브랜치의 동작 원리가 맞는가?
- [ ] 병합과 리베이스의 차이가 정확한가?

**예시**
```
✅ "git add는 파일을 스테이징 영역에 추가합니다.
   이는 다음 커밋에 포함될 변경사항을 선택하는 것입니다."

❌ "git add는 파일을 저장합니다." (부정확)
```

### 실무 적합성

**점검 사항**
- [ ] 예시가 현장에서 사용하는 방식인가?
- [ ] 더 나은 방법이 있지 않은가?
- [ ] 팀 협업 관점에서 적절한가?

**예시**
```
✅ "매일 시작할 때 git pull로 최신 코드를 받으세요"

❌ "git fetch로 원격 코드를 확인한 후 git merge하세요"
(정확하지만 초보자에게는 복잡)
```

### 위험성 경고

**필수 포함 사항**
- ⚠️ --hard 옵션: 복구 불가능
- ⚠️ --force push: 팀원 작업 덮어쓰기
- ⚠️ reset: 커밋 삭제
- ⚠️ rebase (이미 push한 커밋): 히스토리 충돌

**표현 예시**
```
⚠️ 주의: git reset --hard는 변경사항을 완전히 삭제합니다!
로컬에만 있는 커밋에만 사용하세요.
```

## 📊 평가 방식

### 이슈 분류

**Critical (즉시 수정)**
- [ ] 기술적으로 잘못된 설명
- [ ] 실행 불가능한 명령어
- [ ] 데이터 손상 위험을 경고하지 않음

**Major (수정 권장)**
- [ ] 더 나은 방법이 있음
- [ ] 실무와 다른 접근
- [ ] 모든 OS에서 동작하지 않음

**Minor (참고)**
- [ ] 문법 미세한 개선
- [ ] 명령어 옵션 추가 설명 가능
- [ ] 더 최신 버전 사용 가능

## ✅ 체크리스트

- [ ] 모든 git 명령어 검증
- [ ] 개념 설명 정확성 확인
- [ ] 실무 적합성 평가
- [ ] 위험성 명시 여부 확인
- [ ] 모든 OS 호환성 검토
- [ ] review_logs/chapterN_tech_review.md 작성
