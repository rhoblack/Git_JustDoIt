5장: 실전 상황 - 현실에서 만나는 문제들

실제 프로젝트에서 자주 마주치는 5가지 상황과 해결법!

🎯 이 장을 마치면 다음을 할 수 있습니다:

  • 실수로 커밋한 민감한 파일을 제거할 수 있다
  • 이전 버전으로 안전하게 되돌릴 수 있다
  • 다른 브랜치의 특정 파일만 가져올 수 있다
  • 팀 작업에서 최신 코드를 유지하는 방법을 알 수 있다
  • 잘못된 브랜치에 커밋한 것을 옮길 수 있다

💡왜 배우나요?

지금까지 Git의 기본 기능을 배웠습니다. 이 장에서는 실제로 일어나는 상황을 재현하고 직접 해결해봅니다.

각 시나리오는 이런 구조로 진행됩니다:

  1. 상황 설명 - 어떤 문제인가?
  2. 상황 재현 - 직접 이 문제를 만들어보기
  3. 해결 방법 - 단계별로 해결하기
  4. 예방법 - 다시 안 일어나게 하기

🗑️시나리오 1: 실수로 비밀 파일을 커밋했어요!

상황: 비밀번호가 적힌 config.txt 파일을 실수로 커밋하고 push까지 했습니다. 이 파일을 Git에서 제거해야 합니다!

상황 재현하기 (직접 따라해보세요)

$ mkdir secret-test && cd secret-test
$ git init
$ echo "password=1234" > config.txt
$ echo "Hello World" > index.html
$ git add .
$ git commit -m "Initial commit with config"

이제 config.txt(비밀번호 포함)가 Git에 커밋된 상태입니다.

해결 방법

Step 1: 파일을 Git 추적에서 제거 (파일은 유지)
$ git rm --cached config.txt

--cached는 "Git에서만 제거하고, 실제 파일은 그대로 두겠다"는 뜻입니다.

Step 2: .gitignore에 추가
$ echo "config.txt" >> .gitignore
Step 3: 커밋하기
$ git add .gitignore
$ git commit -m "Remove config.txt from tracking, add to gitignore"
Step 4: push하기 (원격 저장소가 있는 경우)
$ git push
Step 5: 확인하기
$ git status

📊 예상 결과: config.txt가 더 이상 추적되지 않습니다.

$ ls

📊 예상 결과: config.txt 파일은 여전히 폴더에 있습니다. Git에서만 제거된 것입니다.

✅ 해결!
비밀 파일이 더 이상 Git에 추적되지 않습니다.
⚠️ 중요: 이미 공개된 비밀번호는 반드시 변경하세요!
Git에서 파일을 제거해도, 이전 커밋 기록에는 남아있습니다. 한 번이라도 GitHub에 올라간 비밀번호는 반드시 새 비밀번호로 변경해야 합니다.

예방법

프로젝트 시작할 때 .gitignore를 먼저 만드세요!

# .gitignore 파일 - 프로젝트 시작 시 생성
.env
config.txt
*.key
*.pem
password*

⏮️시나리오 2: 이전 버전으로 되돌리고 싶어요!

상황: 지난주까지는 잘 작동하던 코드인데, 이후 여러 커밋을 했더니 문제가 생겼습니다. 지난주 상태로 돌아가고 싶습니다.

상황 재현하기

$ mkdir rollback-test && cd rollback-test
$ git init
$ echo "v1: Working code" > app.txt
$ git add . && git commit -m "v1: Working version"

$ echo "v2: Added feature" > app.txt
$ git add . && git commit -m "v2: Add new feature"

$ echo "v3: Broken code!" > app.txt
$ git add . && git commit -m "v3: Refactor (broke something)"

이제 v3는 깨졌고, v1으로 돌아가고 싶은 상태입니다.

해결 방법 A: revert로 안전하게 (추천)

이 방법이 안전한 이유

revert는 기존 커밋을 삭제하지 않고, "되돌리는 새 커밋"을 만듭니다. 기록이 모두 남으므로 팀 작업에서 안전합니다. 이미 push한 커밋도 이 방법으로 되돌릴 수 있습니다.

Step 1: 커밋 기록 확인
$ git log --oneline

📊 예상 결과:

c3c3c3c (HEAD -> master) v3: Refactor (broke something)
b2b2b2b v2: Add new feature
a1a1a1a v1: Working version
Step 2: v3과 v2를 되돌리기
$ git revert --no-commit c3c3c3c
$ git revert --no-commit b2b2b2b
$ git commit -m "Revert to v1 state"

--no-commit은 각 revert를 개별 커밋으로 만들지 않고, 마지막에 한 번에 커밋하게 합니다.

Step 3: 확인
$ cat app.txt

📊 예상 결과: v1: Working code - v1 상태로 돌아왔습니다!

✅ 해결!
안전하게 이전 버전으로 되돌렸습니다. 모든 기록이 남아있습니다.

해결 방법 B: reset으로 강력하게 (로컬 전용)

안심하세요

이 방법은 아직 push하지 않은 로컬 커밋에만 사용하면 안전합니다. 실수해도 git reflog로 복구할 수 있습니다.

$ git reset --hard a1a1a1a # v1의 해시값

v1 이후의 모든 커밋이 삭제됩니다. push하지 않은 경우에만 사용하세요.

⚠️ 이미 push한 경우 reset + force push는 위험합니다
이미 push한 커밋을 reset하면 git push --force가 필요합니다. 이는 팀원의 작업을 덮어쓸 수 있으므로, 반드시 팀원에게 알리고 함께 진행하세요. 혼자 작업하는 개인 브랜치에서만 사용을 권장합니다.

🔀시나리오 3: 다른 브랜치의 파일 일부만 가져오고 싶어요!

상황: feature/profile 브랜치에 여러 파일을 수정했는데, 그 중 profile.html만 master에 가져오고 싶습니다. 나머지 변경은 아직 준비가 안 됐습니다.

상황 재현하기

$ mkdir partial-test && cd partial-test
$ git init
$ echo "Home" > index.html
$ git add . && git commit -m "Initial commit"

# feature 브랜치에서 여러 파일 수정
$ git checkout -b feature/profile
$ echo "Profile page" > profile.html
$ echo "Settings (not ready)" > settings.html
$ git add . && git commit -m "Add profile and settings"

# master로 돌아가기
$ git checkout master

이제 master에서 profile.html만 가져오고 싶습니다.

해결 방법: 특정 파일만 가져오기

Step 1: 다른 브랜치에서 특정 파일 가져오기
$ git checkout feature/profile -- profile.html

-- 뒤에 파일명을 적으면 해당 파일만 가져옵니다.

Step 2: 확인하고 커밋
$ ls

📊 예상 결과: index.html과 profile.html이 있습니다. settings.html은 없습니다!

$ git add profile.html
$ git commit -m "Add profile page from feature branch"
✅ 해결!
원하는 파일만 선택적으로 가져왔습니다.
💡 여러 파일 가져오기
git checkout feature/profile -- file1.html file2.css file3.js
파일명을 공백으로 구분하여 여러 개를 한 번에 가져올 수 있습니다.

🔄시나리오 4: 내 브랜치가 master와 너무 달라졌어요!

상황: feature 브랜치에서 일주일째 작업 중인데, 팀원들이 계속 master에 코드를 올리고 있습니다. 나중에 병합할 때 충돌이 너무 많을 것 같아 걱정됩니다.

상황 재현하기

$ mkdir sync-test && cd sync-test
$ git init
$ echo "Original" > app.txt
$ git add . && git commit -m "Initial"

# feature 브랜치에서 작업
$ git checkout -b feature/mywork
$ echo "My feature" > feature.txt
$ git add . && git commit -m "Add my feature"

# master에서 다른 사람이 작업 (시뮬레이션)
$ git checkout master
$ echo "Team update" > team.txt
$ git add . && git commit -m "Team added new file"

이제 master와 feature 브랜치가 각각 다른 변경사항을 가지고 있습니다.

해결 방법: 정기적으로 master 합치기 (추천)

Step 1: feature 브랜치에서 master를 합치기
$ git checkout feature/mywork
$ git merge master

📊 예상 결과:

Merge made by the 'ort' strategy.
team.txt | 1 +
1 file changed, 1 insertion(+)
Step 2: 확인하기
$ ls

📊 예상 결과: app.txt, feature.txt, team.txt 모두 있습니다! master의 최신 코드가 내 브랜치에 반영되었습니다.

✅ 해결!
내 브랜치에 master의 최신 코드가 반영되었습니다. 충돌이 있었다면 이 시점에서 작은 범위로 해결할 수 있습니다.

팀 협업 Best Practices

습관 이유
매일 시작 전 git pull 최신 코드로 시작하면 충돌이 줄어듦
작은 단위로 자주 커밋 문제가 생겨도 작은 범위에서 해결 가능
2~3일마다 master 병합 차이가 커지기 전에 합치면 충돌이 적음
PR로 병합하기 코드 리뷰로 실수 방지
팀원과 소통하기 같은 파일 동시 수정 방지

😱시나리오 5: 잘못된 브랜치에 커밋했어요!

상황: feature 브랜치에서 작업해야 했는데, 실수로 master에 커밋해버렸습니다!

상황 재현하기

$ mkdir wrong-branch-test && cd wrong-branch-test
$ git init
$ echo "Base" > base.txt
$ git add . && git commit -m "Initial"

# 실수로 master에서 작업!
$ echo "This should be in feature branch" > oops.txt
$ git add . && git commit -m "Feature work (on wrong branch!)"

해결 방법

안심하세요

이 방법은 아직 push하지 않은 커밋에 안전하게 사용할 수 있습니다. 커밋 내용은 절대 사라지지 않고, 올바른 브랜치로 옮겨집니다.

Step 1: 새 브랜치를 만들어 커밋 보존
$ git branch feature/moved-work

현재 위치(실수 커밋 포함)에서 새 브랜치를 만듭니다. 아직 이동은 하지 않습니다.

Step 2: master에서 실수 커밋 제거
$ git reset --hard HEAD~1

master에서 마지막 커밋이 제거됩니다. 하지만 feature/moved-work 브랜치에는 남아있습니다!

Step 3: 확인하기
$ ls # master: oops.txt 없음
$ git checkout feature/moved-work
$ ls # feature: oops.txt 있음!
✅ 해결!
master는 깨끗해졌고, 커밋은 올바른 브랜치로 옮겨졌습니다!

⚡빠른 참조 - 자주 사용하는 명령어

기본 작업 (매일 사용)

$ git status # 현재 상태 확인
$ git add . # 모든 변경 파일 스테이징
$ git commit -m "msg" # 변경사항 저장
$ git push # GitHub에 올리기
$ git pull # GitHub에서 받기

브랜치 작업

$ git branch # 브랜치 목록
$ git checkout -b name # 새 브랜치 만들고 이동
$ git checkout name # 브랜치 전환
$ git merge name # 브랜치 합치기
$ git branch -d name # 브랜치 삭제

기록 확인

$ git log --oneline # 커밋 기록 (간단히)
$ git diff # 변경 내용 비교
$ git show abc1234 # 특정 커밋 상세 보기
$ git blame file.txt # 누가 수정했는지 확인

실수 바로잡기

$ git revert abc1234 # 안전하게 커밋 되돌리기
$ git reset --soft HEAD~1 # 커밋만 취소 (파일 유지)
$ git stash # 임시 저장
$ git stash pop # 임시 저장 복구
$ git reflog # 모든 작업 기록 (복구용)

🎓축하합니다! Git 입문을 마쳤습니다!

핵심 체크리스트

배운 것 관련 명령어
저장소 만들기 git init
파일 저장하기 git add, git commit
GitHub 활용 git push, git pull
브랜치와 병합 git branch, git merge
충돌 해결 수동 편집 후 git add, git commit
실수 되돌리기 git revert, git reset
임시 저장 git stash
복구 git reflog

다음에 배울 것들

  • GitHub Actions: 자동화된 테스트와 배포
  • 커밋 컨벤션: 팀에서 통일된 커밋 메시지 규칙
  • Git alias: 자주 쓰는 명령어 줄여쓰기
  • Git hooks: 커밋 전 자동 검사

유용한 Git alias 설정

$ git config --global alias.st status
$ git config --global alias.co checkout
$ git config --global alias.br branch
$ git config --global alias.lg "log --oneline --graph"

이제 git st만 입력하면 git status와 같습니다!

마지막 조언
